\begin{abstract}
Silicon lifecycle management (SLM) uses hardware and system telemetry to monitor a device after it leaves manufacturing. A deployed processor may see workload changes, firmware updates, voltage and thermal stress, aging, and security attacks. These effects appear in telemetry, but the detector must be small enough to run near the device and clear enough to explain an alert. This paper presents EXACT, an edge-resident telemetry method for SLM. Here, edge-resident means that the anomaly decision is made locally, without sending raw telemetry to a server. EXACT learns a benign reference from healthy data, builds a causal telemetry graph, selects a small set of compute, memory, and sensor signals, and scores those signals with Causal Integrated Anomaly Scoring (CINTAS). CINTAS is a fixed-point detector, meaning that it uses scaled integer arithmetic rather than floating-point arithmetic. The paper studies EXACT as a deployable design, not only as an anomaly detector. It measures how feature budget, decision-block length, aggregation, score weighting, score mixing, and fixed-point precision affect detection quality, latency, telemetry bandwidth, numerical error, and hardware cost. It also defines a lifecycle path for drift monitoring and benign recalibration. Finally, it connects the software model to hardware by using add/multiply operator costs, register-transfer-level (RTL) golden vectors, and a field-programmable gate array (FPGA) validation path. The result is a reproducible framework for compact, explainable, and hardware-aware SLM.
\end{abstract}

\section{Introduction}

Silicon lifecycle management (SLM) monitors a device across design, test, deployment, and field operation. After deployment, a processor does not run in a fixed state. Workloads change. Firmware and software change. Voltage, temperature, and aging shift device behavior. Security attacks can also perturb execution. SLM uses telemetry to observe these changes and support detection, diagnosis, and service decisions \cite{slm_survey,self_aware_silicon}.

Telemetry means measurements collected from the device or host system. Examples include performance counters, memory counters, power readings, voltage readings, temperature sensors, operating-system statistics, and profiling signals. These signals can reveal abnormal behavior before a failure becomes visible to the user. The difficulty is that telemetry streams are high dimensional, platform dependent, and often noisy. A useful SLM detector must therefore reduce telemetry to a small set of signals, make decisions with low latency, and provide enough context to explain why it raised an alert.

This requirement rules out many convenient solutions. Supervised learning depends on labeled anomalies, but field anomalies are rare and often lack precise start times. Large floating-point models can work offline, but they are difficult to place in a small on-device monitor. Cloud-assisted methods can support detailed diagnosis, but they move data off the device and add latency. A practical SLM method should learn mainly from benign data, where benign means known healthy operation. It should also run close to the hardware and report which telemetry signals contributed to the decision.

Several recent systems address parts of this problem. E-SCOUT uses telemetry feature ranking and on-chip outlier detection with cloud-assisted diagnosis \cite{escout}. OCTANE uses fixed-point on-chip anomaly scoring and workload-independent feature ranking \cite{octane}. X-OCTANE adds explainable feature ranking by combining Causal-Preserving Mutual Information (CP-MI) with SHapley Additive exPlanations (SHAP) \cite{xoctane}. CP-MI measures dependence among telemetry signals while preserving causal structure. SHAP assigns feature-attribution scores that show how much each signal contributes to a model output. TRACK studies representation similarity for fleet-level monitoring across homogeneous and heterogeneous platforms \cite{track}. DICE uses a behavioral micro-twin and conformal calibration for host-side continuous test when only operating-system telemetry is available \cite{dice}.

These systems show the value of telemetry for SLM, but they also leave a design question. How can an SLM detector combine local scoring, causal signal selection, low hardware cost, and lifecycle maintenance in one reproducible flow? EXACT answers this question by treating telemetry analysis as both a learning problem and a deployment problem.

EXACT stands for Edge-eXplainable Autonomous Causal Telemetry. It uses benign data to estimate a healthy reference for each telemetry signal. It then learns a sparse causal telemetry graph and ranks signals by their importance. A feature budget selects the top signals from compute, memory, and sensor domains. CINTAS then scores only those selected signals. A decision block is a fixed group of consecutive telemetry samples. CINTAS produces one anomaly decision per block by aggregating sample scores and comparing the block score with a benign threshold.

The main idea is simple. A device should not need to monitor every available signal at runtime. It should monitor a small, stable, and interpretable subset. It should also know the cost of that subset. The number of selected features affects arithmetic operations, telemetry bandwidth, power, and area. The decision-block length affects latency. The fixed-point precision affects numerical error and hardware cost. These choices must be measured together, not tuned in isolation.

This paper makes those choices explicit. It studies feature budget, decision-block length, aggregation operator, feature weighting, score mixing, and fixed-point precision. It reports detection metrics, calibration metrics, latency, bandwidth, fixed-point error, and hardware estimates. It also prepares a hardware path by exporting fixed-point golden vectors for RTL simulation and FPGA validation. RTL describes the cycle-level hardware behavior of the detector. An FPGA is a reconfigurable chip that can test the detector before an application-specific implementation.

The paper also considers platform coverage. The main hardware path uses CPU--DRAM telemetry because it exposes counters and sensors that map naturally to on-chip or near-sensor deployment. A macOS dataset can still be useful, but it should be used as a separate limited-observability case study. macOS host telemetry tests whether the scoring and calibration ideas survive when low-level model-specific registers are unavailable. It should not be used to claim the same on-chip hardware cost as the CPU--DRAM platforms, because the signal source and access path are different.

The main contributions are as follows.

\begin{itemize}
    \item We present a reproducible EXACT flow that connects benign calibration, causal telemetry ranking, top-$k$ feature selection, CINTAS scoring, thresholding, drift monitoring, and hardware-cost evaluation.
    \item We define a design-space study for CINTAS. The study sweeps feature budget, decision-block length, score mixing, aggregation, feature weighting, and fixed-point precision.
    \item We report deployment-oriented metrics: detection quality, probability calibration, latency, feature bandwidth, fixed-point error, add/multiply counts, area estimates, power estimates, delay, and cycles.
    \item We include a lifecycle procedure for benign drift. The procedure freezes an initial benign reference, monitors false-positive drift, and supports threshold-only or full recalibration using safe benign windows.
    \item We define a hardware validation path that moves from Python fixed-point scoring to RTL golden vectors, FPGA simulation, and synthesis reports.
    \item We position macOS host telemetry as a limited-observability validation case that complements, but does not replace, hardware-counter platforms.
\end{itemize}

\section{Background}

\subsection{Silicon Lifecycle Management and Telemetry}

SLM uses telemetry to support reliability, security, and performance decisions across a device lifetime. In this paper, telemetry means measured signals collected from hardware or the host operating system. Hardware telemetry includes counters and sensors such as instructions, cycles, cache misses, memory traffic, voltage, temperature, and power. Host telemetry includes operating-system measurements such as CPU utilization, memory pressure, disk activity, network activity, interrupts, and process counts.

The distinction matters. Hardware telemetry gives a direct path to on-chip or near-sensor scoring. Host telemetry is easier to collect on deployed systems but is less direct. A method that works on both types of data has broader value, but the results must be reported separately because the deployment assumptions differ.

An SLM analytics stack has three parts. The first part senses the device. The second part transports and aligns telemetry. The third part converts telemetry into decisions. EXACT focuses on the third part while keeping the first two parts visible. It asks which signals are available, which signals are selected, how they are scored, and what the scoring hardware costs.

\subsection{Telemetry-Based Anomaly Detection and Diagnosis}

An anomaly is a telemetry pattern that deviates from benign operation. In SLM, an anomaly can come from voltage droop, RowHammer, Spectre, thermal stress, workload shift, firmware change, aging, or another fault mode. Detection means deciding whether an anomaly is present. Diagnosis means explaining or classifying the source of the anomaly.

Many anomaly detectors learn from benign data because labeled failures are rare. Isolation Forest, one-class support vector machines, autoencoders, and distance-based methods are common choices. These methods can be effective in software, but they may require floating-point computation, large memory, or off-device analysis. They may also give weak diagnostic context unless another explanation method is added.

E-SCOUT and OCTANE show how telemetry detectors can move closer to hardware. E-SCOUT ranks telemetry features and performs on-chip outlier detection, then uses a cloud layer for diagnosis. OCTANE uses fixed-point arithmetic to produce on-chip anomaly scores. X-OCTANE adds a stronger explanation path by ranking features with CP-MI and SHAP. These methods motivate EXACT, but EXACT uses causal telemetry selection with an edge-resident CINTAS detector and treats hardware cost, calibration, and lifecycle drift as first-order design variables.

\subsection{Explainable Feature Ranking}

Feature ranking orders telemetry signals by importance. A good ranking should select signals that improve detection and also make physical sense. For example, a voltage droop should affect voltage, power, timing, and performance signals. A memory disturbance should affect memory traffic and cache behavior. Ranking only by model accuracy may select unstable or redundant signals. Ranking only by correlation may miss the signal's role in the detector.

Prior work offers two useful ideas. CP-MI ranks signals by multivariate dependence while keeping causal structure in view. SHAP ranks signals by their contribution to a model output. X-OCTANE shows that combining these ideas can improve interpretability and diagnosis. EXACT uses a related principle: the selected feature set should be compact, stable, and explainable. The selected signals are grouped into compute, memory, and sensor domains so that each alert can be tied back to a physical part of the system.

\subsection{Hardware-Aware Edge Analytics}

Edge analytics means making the anomaly decision close to the device. In this paper, it means that CINTAS can run locally using the selected telemetry signals. This creates hardware constraints. The detector must use few features, few operations, and small state. It must also have predictable latency.

Fixed-point arithmetic helps meet these constraints. A fixed-point value is a scaled integer. It can represent normalized telemetry without a floating-point unit. CINTAS uses fixed-point add, multiply, absolute-value, compare, and accumulation operations. The feature budget determines how many operations are needed per sample. The decision-block length determines how often the detector emits a decision. The fixed-point precision determines the trade-off between numerical error and hardware cost.

Hardware cost must be reported with the detection result. EXACT therefore tracks add and multiply counts, area, power, delay, cycles, feature bandwidth, and fixed-point error. The software model exports golden vectors, which are known input-output examples used to verify the RTL implementation.

\subsection{Limited-Observability Host Telemetry}

Not every platform exposes the same counters. Some deployed systems do not allow direct access to model-specific registers or low-level sensors. macOS is a useful example because it can provide operating-system and profiler-derived telemetry but not the same low-level interface used by Linux CPU--DRAM experiments.

The macOS data from the DICE study can strengthen this paper if it is used carefully. It should test portability under limited observability. It can answer whether benign calibration, compact feature selection, and block-level scoring still work when the signals are host-level rather than hardware-counter-level. It can also support the lifecycle story because the dataset includes workload and stressor variation.

The macOS case should be reported as a separate experiment lane. It should not be mixed into the hardware-cost table for CINTAS, since the access path is host-side and does not imply the same on-chip implementation. A clear paper structure is to report CPU--DRAM platforms for hardware-aware CINTAS deployment and macOS for limited-observability robustness.

\subsection{Position of This Work}

The starting point is a compact causal telemetry detector. The goal here is to engineer that detector for practical SLM use. That requires more than a single accuracy number. It requires a design-space study, a hardware-cost model, a reproducibility record, a drift and recalibration plan, and a clear account of how the method behaves when observability changes across platforms.

This paper therefore treats EXACT as a complete SLM workflow. It starts with benign telemetry, selects a compact and explainable feature set, scores the selected features with fixed-point arithmetic, checks the detector across design choices, prepares RTL and FPGA validation, and separates direct hardware-counter platforms from host-side limited-observability platforms.
